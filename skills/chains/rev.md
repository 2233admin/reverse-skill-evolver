# chains-rev 决策骨架（场景→判据→转向）

> 形式借鉴 ARTEX `agent/chainskel/`（AGPL-3.0）的决策骨架结构；**本文内容全部蒸馏自本包
> `skills/field-journal/` 自有种子与先例库，未复制 ARTEX 任何文本。**
> 用法：路由命中二进制逆向类任务时由 `route` 输出带入；执行前对照本表定位当前场景。

## 一、入口分诊

- 场景:拿到陌生 ELF/PE 第一分钟|判据:先 `file` 确认真实类型——**后缀不可信**（伪装的 .sh 实为 ELF）；再 `readelf -l` 看程序头是否被故意损坏|转向:程序头异常→忽略损坏段只看有效 LOAD；`readelf` 报错改用 `rabin2 -I`（更容错）〔seed-001〕
- 场景:判断是否加壳|判据:字符串窗口近乎为空 + 高熵密文块；UPX 特征节名（UPX0/UPX1）或入口为小 stub|转向:标准壳直接脱；脱壳报错→修魔数或用 ESP 定律到 OEP 后 dump 修 IAT〔seed-001〕
- 场景:确认语言与运行时|判据:`strings | grep "go1\."` 定 Go 版本；Go 静态链接会带来 5 万+ 函数|转向:Go → 先恢复符号再分析，别硬读〔seed-002〕

## 二、符号与字符串恢复

- 场景:stripped 二进制找不到入口逻辑|判据:Go 二进制用 GoReSym 恢复 pclntab 结构（函数边界）——**即使被 Garble 混淆也有效**|转向:恢复后按包名过滤，只看 `main.*`〔seed-002〕
- 场景:恢复出的函数名是随机字符|判据:用户函数名被 Garble 随机化，但标准库可用 CFG 签名匹配（不受改名影响）|转向:GoResolver 恢复标准库，剩余手动分析〔seed-002〕
- 场景:字符串窗口几乎为空|判据:字符串被运行时加密，属混淆器特征而非"无字符串"|转向:GoStringUngarbler 批量解密；C/汇编则 xref 高熵密文块找解密器〔seed-002〕
- 场景:相信 IDA 反编译结果|判据:位操作密集的代码（ARM64、位流）Hex-Rays 优化差，反编译不可读|转向:切反汇编视图手动分析，别在反编译上耗时间〔seed-001〕

## 三、算法与密钥定位

- 场景:判断标准算法 vs 自研|判据:搜指纹常量（TEA 0x9e3779b9、SHA256 0x6a09e667、AES S-box）；魔改只动 S-box/轮数/delta，骨架守恒|转向:命中指纹→diff 差异点；无指纹→按黑盒定性〔seed-004〕
- 场景:定位加密密钥|判据:密钥通常在 `crypto/aes.NewCipher` 等构造调用**第一个参数**的来源处；可能是硬编码常量拼接|转向:回溯参数来源；或用完即焚时 hook 密钥生成瞬间〔seed-002〕
- 场景:自定义压缩/解压算法|判据:识别位流操作 + 滑动窗口回拷 = LZSS 类；`lsl`/`cbz` 组合是 ARM64 位流读取特征|转向:用 Python 重写解压器 dump 数据，**对照汇编逐条核对**（位流 refill 路径最易错）〔seed-001〕
- 场景:重写算法的实现结果不对|判据:错误集中在边界值处（如 refill 返回的是新加载字的最高位）|转向:回到汇编逐指令对照，不要凭语义猜〔seed-001〕

## 四、动态与注入链

- 场景:静态分析不再产出新事实|判据:同一区域重复阅读无新增信息|转向:切动态验证；有反调试则静态起手，混淆重则动态 trace〔seed-001〕
- 场景:识别自解压/注入型样本|判据:入口少量初始化 → 调用解压函数 → `mmap(RW)` → 解压到该区域 → `mprotect(RX)` → 跳转|转向:按此模式定位注入点与 payload 入口偏移，跟踪跳转指令确认偏移〔seed-001〕
- 场景:样本一进调试器就退出/走假分支|判据:存在反调试——查 `ptrace`、TracerPid、时间差检测|转向:patch 判定跳转或改返回值最省事；点多而散用批量中和工具〔seed-001〕

## 五、JS / 签名类（同属逆向主路径）

- 场景:抓包看到未知签名参数|判据:webpack 打包后变量名压缩，直接搜 "sign" 噪声大|转向:用 DevTools 的 **initiator/调用栈**回溯，比搜源码快〔seed-004〕
- 场景:签名逻辑读不懂|判据:压缩代码需先格式化；有 SourceMap 直接还原原始代码|转向:Pretty Print + 断点，逐段确认参数处理顺序〔seed-004〕
- 场景:本地复现签名结果不一致|判据:差异几乎总在**参数排序与时间精度**（秒 vs 毫秒）|转向:严格对照源码的 sort 逻辑与 `Math.floor(Date.now()/1000)`〔seed-004〕
- 场景:密钥找不到|判据:密钥常在另一 chunk 中经 require 引入，静态搜不到|转向:在断点处打印变量，或回调调用栈向上找来源〔seed-004〕

## 六、固件与硬件（IoT）

- 场景:拿到固件镜像|判据:先做类型识别与熵分析——熵接近极限说明整体加密，后续提取会失败|转向:按识别结果提取文件系统；提取出空目录说明是私有头，改用切片或更鲁棒的提取工具〔seed-015〕
- 场景:固件已提取|判据:默认凭据、启动脚本、Web 服务程序是最快命中点|转向:先用自动化线索扫描跑一遍，再针对性看凭据文件与启动脚本〔seed-015〕
- 场景:拿到凭据哈希|判据:嵌入式设备常用弱口令|转向:离线爆破；同时并列尝试常见厂商默认凭据〔seed-015〕
- 场景:需要物理接入|判据:PCB 上未占用的排针通常是调试串口；用万用表按启动时电平跳变区分 TX/RX，按铜片接地识别 GND|转向:接转换器时**不接供电线**（设备自供电）；TX/RX 需交叉连接〔seed-015〕
- 场景:串口无字符输出|判据:波特率大概率不匹配|转向:遍历常见波特率；先解决速率再怀疑接线〔seed-015〕
- 场景:串口输出乱码|判据:接线顺序错误或电平不匹配|转向:互换收发两线；确认转换器电平与被测设备一致〔seed-015〕
- 场景:有登录提示但无可用密码|判据:引导阶段常留中断入口|转向:在引导阶段中断，改启动参数直接进单用户 shell，绕开密码〔seed-015〕
- 场景:引导阶段无法中断|判据:厂商关闭了控制台或改了提示符|转向:从固件中找出延迟参数；或用物理手段制造启动失败迫使引导程序进入交互〔seed-015〕
- 场景:进了系统但缺常用工具|判据:精简镜像未含远程服务程序|转向:从外部介质挂载带入静态编译的工具集〔seed-015〕
- 场景:Web 管理界面待测|判据:固件可模拟启动时无需真机|转向:优先用模拟环境跑动态测试，比反复烧写真机快〔seed-015〕

## 七、验证与收尾

- 场景:声称"已还原/已复现"|判据:必须在下游可观测处验证——复现签名能通过接口校验、dump 的 payload 能解释行为|转向:无法验证时降级为 candidate，不写 validated〔seed-004〕
- 场景:工具报"无异常/未检出"|判据:工具阴性只说明"这套规则这次未触发"，不等于目标无问题|转向:关键判断改用最小手工验证，保留证据〔seed-002〕
